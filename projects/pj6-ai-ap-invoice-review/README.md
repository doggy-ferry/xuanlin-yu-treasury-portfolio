# PJ6 — AI-Assisted AP Invoice Review & Exception Triage

A personal portfolio project that demonstrates how an accounts-payable first-pass review can combine **deterministic controls**,
a **limited AI semantic check** and **human review**, and how to evaluate that workflow honestly against a locked ground truth.

> **100% synthetic data.** All company names, addresses, bank accounts, PO numbers, invoice numbers and amounts are fictional.
> The project contains no employer information. It is a personal portfolio project, **not a production AP system**, and it
> **does not approve or execute payments**.

## What it shows

1. Every one of 100 synthetic invoices gets an automatic first-round check.
2. Deterministic Python rules handle numbers, master data, dates and duplicates.
3. The Claude API (Live API Mode) or pre-generated results (Demo Mode) handle only semantic questions: description vs PO,
   vague wording, exception conditions in notes, unreadable evidence.
4. Clean invoices go to a low-risk queue; flagged or low-confidence invoices go to a human queue.
5. A reviewer can approve as normal, confirm an exception, reject an AI flag, escalate, or add a note. Each action is stored
   with time, outcome and note.
6. An evaluator reads the locked ground truth and computes precision, recall, F1, false positives and false negatives for
   manual sampling, rules only, AI only, rules + AI, and the final reviewed result.

## Acceptance protocol (how a team would roll it out)

1. Verify the first normal invoices in full against source documents.
2. After that, review exceptions only.
3. Randomly spot-check auto-passed invoices on an ongoing basis.
4. Escalate exceptions with reason codes and a reference to comparable past cases.

The Overview page presents the same four steps. They are procedure, not results.

## Responsibilities

| Layer | Responsible for |
|---|---|
| Deterministic rules | numeric and master-data controls, duplicates, dates |
| Claude API (limited) | semantic checks and short audit-friendly explanations; flags low confidence |
| Human | final review, accepting or rejecting exceptions, any disposition; nothing is auto-approved |

## Demo Mode vs Live API Mode

- **Demo Mode (default; works with no API key).** Uses `data/precomputed_ai_results.json`. **These results are pre-generated by a
  deterministic offline simulation (keyword and word-overlap heuristics), not by Claude**, and the UI says so. They exist so the
  demo can run publicly and for free. They are not a measure of Claude's accuracy.
- **Live API Mode (local or secure backend only).** Needs your own `ANTHROPIC_API_KEY` and `ANTHROPIC_MODEL` in the server's
  environment. The browser never sees the key and never calls Anthropic. At most 5 invoices per request, bounded retries,
  one call per invoice, call log (no key, no invoice text) and an estimated-cost counter with configurable placeholder prices.
  In this repository the live path is verified only with a fake SDK client; it has not been run against the real API.

## Run locally

```powershell
python -m venv .venv
.\.venv\Scripts\python -m pip install -r requirements-dev.txt
.\.venv\Scripts\python -m uvicorn app.main:app --port 8000
# open http://127.0.0.1:8000
```

Static demo without a backend: serve the `frontend/` folder with any static server; it falls back to `frontend/snapshot.json`
(rebuild with `python scripts/export_static_snapshot.py`). Review actions are then kept in the browser only.

Live mode (optional, your own key):

```powershell
copy .env.example .env   # then set the values in your shell; .env is git-ignored and never read by the front end
$env:ANTHROPIC_API_KEY = "<your key>"; $env:ANTHROPIC_MODEL = "<model id>"
```

Regenerate everything: `python scripts/generate_synthetic_data.py`, `python scripts/generate_demo_results.py`,
`python scripts/export_static_snapshot.py`, `python scripts/generate_validation_report.py`.

## Tests

```powershell
.\.venv\Scripts\python -m pytest -q
```

Covers data generation and reproducibility, the 70/30 split and exception distribution, each rule, ground-truth isolation,
AI schema and failure handling with a fake client, evaluation maths, key-leak scanning, and real-browser checks at 390, 430, 768
and 1440 px (no horizontal overflow, 44 px touch targets, table-to-card layout, no ground truth in Review mode). Browser tests
are skipped if no Chromium-based browser is available.

## Data

`data/` holds `suppliers`, `purchase_orders`, `goods_receipts`, `invoices`, `invoice_lines`, `ground_truth` (CSV, locked by
`ground_truth.lock`) and `precomputed_ai_results.json`. Generation is seeded and byte-reproducible. 70 invoices are normal
(including deliberate benign decoys such as vague wording, partial receipts and one-cent rounding) and 30 contain one or two
known exceptions across 12 types (including missing required fields).

## What the numbers mean

Metrics are computed live from the ground truth and apply **only to this synthetic 100-invoice set**. They are not production
accuracy and must not be quoted as such. The manual-sampling row is an assumption model, and the "final reviewed" row uses a
scripted demo reviewer unless you record your own actions.

## What this is not

Not a payment system, not an ERP, not a trained model, not evidence of savings or production results, and not a replacement for
AP staff or auditors. See `docs/` for architecture, the control matrix and the validation report.
